Tidy data

The same data, many shapes

The same information can be stored in many different table layouts.

Most of them make analysis harder than it needs to be.

Tidy data is one consistent layout that fits the tidyverse, so dplyr, ggplot2, and the rest all work without reshaping first.

Data semantics

Before we can say what makes a dataset tidy, we need a shared vocabulary for what is in it. A dataset is a collection of values, each one a number or a string.

Every value belongs to both a variable and an observation:

  • A variable holds all the values that measure the same attribute (height, temperature, duration) across units
  • An observation holds all the values measured on the same unit (a person, a day, a country-year) across attributes

The three rules

  • Each variable forms a column
  • Each observation forms a row
  • Each cell is a single measurement

If your table follows these three rules, it is tidy. Almost everything else this module does is about getting there.

Tidy in practice

tidyr ships with the same dataset in several shapes. This one is tidy:

A messy version

The same numbers, but the values cases and population are hidden in a type column:

Now a single observation (one country-year) is spread over two rows.

Why tidy data pays off

  • One consistent layout to learn, instead of one per dataset
  • Variables live in columns, exactly where ggplot2 and dplyr expect them
  • Vectorized operations work naturally down each column
  • Less time reshaping, more time analysing

Reshaping with tidyr

What tidyr does

tidyr is the tidyverse package for reshaping tables into tidy form. It is loaded with the tidyverse.

Its main jobs:

  • Pivoting: switching between long and wide layouts
  • Splitting and combining columns
  • Nesting and unnesting columns
  • Treating missing values

Pivoting: what is it?

Pivoting reshapes a table by moving information between rows and columns, without changing the data itself.

Two directions:

Longer

Many columns into fewer columns and more rows.

Wider

Fewer columns into many columns and fewer rows.

They are inverses of each other: pivot_longer() undoes pivot_wider() and vice versa.

pivot_longer()

When to go longer

A common problem: column names are values, not variables.

table4a
# A tibble: 3 × 3
  country     `1999` `2000`
  <chr>        <dbl>  <dbl>
1 Afghanistan    745   2666
2 Brazil       37737  80488
3 China       212258 213766

1999 and 2000 are years, not variable names. The numbers are all cases.

pivot_longer()

table4a |>
  pivot_longer(
    cols = c(`1999`, `2000`),
    names_to = "year",
    values_to = "cases"
  )
# A tibble: 6 × 3
  country     year   cases
  <chr>       <chr>  <dbl>
1 Afghanistan 1999     745
2 Afghanistan 2000    2666
3 Brazil      1999   37737
4 Brazil      2000   80488
5 China       1999  212258
6 China       2000  213766

Reading the arguments

  • cols: which columns to pivot (the year columns here)
  • names_to: name of the new column holding the old column names
  • values_to: name of the new column holding the old cell values

The columns not listed in cols are kept as identifiers, repeated down the new rows.

pivot_wider()

When to go wider

The opposite problem: one observation is spread over several rows. Recall table2:

head(table2, 4)
# A tibble: 4 × 4
  country      year type          count
  <chr>       <dbl> <chr>         <dbl>
1 Afghanistan  1999 cases           745
2 Afghanistan  1999 population 19987071
3 Afghanistan  2000 cases          2666
4 Afghanistan  2000 population 20595360

cases and population should be two columns, not two rows.

pivot_wider()

table2 |>
  pivot_wider(
    names_from = type,
    values_from = count
  )
# A tibble: 6 × 4
  country      year  cases population
  <chr>       <dbl>  <dbl>      <dbl>
1 Afghanistan  1999    745   19987071
2 Afghanistan  2000   2666   20595360
3 Brazil       1999  37737  172006362
4 Brazil       2000  80488  174504898
5 China        1999 212258 1272915272
6 China        2000 213766 1280428583

Reading the arguments

  • names_from: the column whose values become new column names
  • values_from: the column whose values fill the new columns

pivot_wider() often makes data less tidy. It is most useful for building summary tables for humans to read, not for further analysis.

Combining several columns into one

unite() is the reverse, gluing columns together:

table5 <- table1 |>
  unite("country_year", country, year, sep = "_")

Nesting columns

nest() collapses a group of rows into a single cell holding a small tibble:

nested <- table1 |>
  nest(data = c(year, cases, population))

nested
# A tibble: 3 × 2
  country     data            
  <chr>       <list>          
1 Afghanistan <tibble [2 × 3]>
2 Brazil      <tibble [2 × 3]>
3 China       <tibble [2 × 3]>

One row per country, with all its measurements tucked away in data.

Nesting shines when you want to fit one model or make one plot per group, using a column of tibbles.

Treating missing values

tidyr has dedicated tools for NA:

Function What it does
drop_na() remove rows containing NA
replace_na() swap NA for a chosen value
fill() carry the last value down (or up)
complete() add rows for missing combinations

Missing values in action

sales <- tibble(
  quarter = c("Q1", NA, NA, "Q2"),
  revenue = c(100, 150, NA, 200)
)

sales |>
  fill(quarter) |>
  replace_na(list(revenue = 0))
# A tibble: 4 × 2
  quarter revenue
  <chr>     <dbl>
1 Q1          100
2 Q1          150
3 Q1            0
4 Q2          200

Joining data

Why join?

Real projects rarely keep everything in one table.

  • Measurements in one file, site descriptions in another
  • Short codes in your data, with their full meanings stored in a separate lookup table
  • Results you produced, joined back to the original records

Joins combine two tables by matching rows on a shared key.

Two small tables

dplyr ships two tiny tables that share a name column:

band_members
# A tibble: 3 × 2
  name  band   
  <chr> <chr>  
1 Mick  Stones 
2 John  Beatles
3 Paul  Beatles
band_instruments
# A tibble: 3 × 2
  name  plays 
  <chr> <chr> 
1 John  guitar
2 Paul  bass  
3 Keith guitar

The mutating joins

All take the form *_join(x, y) and add the columns of y to x. They differ in which rows they keep:

Function Keeps
inner_join() rows matched in both tables
left_join() all rows of x
right_join() all rows of y
full_join() all rows of either table

Picturing the joins

Diagram from Wickham, Çetinkaya-Rundel & Grolemund, R for Data Science (2e), licensed CC BY-NC-ND 3.0.

left_join(): keep everything in x

band_members |>
  left_join(band_instruments, by = "name")
# A tibble: 3 × 3
  name  band    plays 
  <chr> <chr>   <chr> 
1 Mick  Stones  <NA>  
2 John  Beatles guitar
3 Paul  Beatles bass

Mick has no instrument, so the new column is NA. No member is dropped.

inner_join(): keep only matches

band_members |>
  inner_join(band_instruments, by = "name")
# A tibble: 2 × 3
  name  band    plays 
  <chr> <chr>   <chr> 
1 John  Beatles guitar
2 Paul  Beatles bass

Only John and Paul appear in both tables, so only they survive.

full_join(): keep everyone

band_members |>
  full_join(band_instruments, by = "name")
# A tibble: 4 × 3
  name  band    plays 
  <chr> <chr>   <chr> 
1 Mick  Stones  <NA>  
2 John  Beatles guitar
3 Paul  Beatles bass  
4 Keith <NA>    guitar

Everyone is kept; gaps on either side become NA.

The key with by

by names the column(s) used to match rows:

  • by = "name": match on a shared column name
  • by = join_by(id == person_id): match columns with different names
  • omit it and dplyr matches on all shared names, printing a message

Always be explicit about the key. A silent match on the wrong columns is a hard bug to spot.

Filtering joins

Two joins use y only to filter x, never adding columns:

band_members |>
  anti_join(band_instruments, by = "name")
# A tibble: 1 × 2
  name  band  
  <chr> <chr> 
1 Mick  Stones
  • semi_join(): keep rows of x that have a match
  • anti_join(): keep rows of x that have no match

Metadata

What is metadata?

Metadata is data about your data: the documentation that lets someone else (or future you) understand and reuse a project.

A dataset without metadata is a pile of numbers. With metadata, it is evidence.

Documenting a project

Project-level documentation usually lives in a README file and covers:

  • General information: title, author, purpose, date
  • Access information: licence, how to cite, where it lives
  • Methodological information: how the data were collected and processed

Documenting the data itself

For the data, you write a data dictionary (also called a codebook).

It describes each variable. At a minimum:

  • the variable name as it appears in the file
  • a plain-language description

Often also: units, type, allowed values, and codes for missing data.

A data dictionary as a table

variable description units
country country name
year year of measurement
cases confirmed TB cases count
population population that year people

For the capstone project, save it as dictionary.csv in your processed data folder.

Organizing a project

A place for everything

A predictable folder structure means anyone can find their way around:

.
├── R
│   └── 01-data-preparation.R
├── data
│   ├── processed
│   │   ├── README.md
│   │   ├── dictionary.csv
│   │   └── analysis.csv
│   └── raw
│       └── survey_05112025.xlsx
├── docs
│   ├── index.qmd
│   └── index.html
└── project.Rproj

Reading the tree

  • R/: scripts that do things, mainly data preparation
  • data/raw/: the original files, never edited by hand
  • data/processed/: clean data plus its README and dictionary
  • docs/: the rendered report and its source
  • project.Rproj: opens the project in RStudio

One golden rule

Raw data is read-only.

You never overwrite the files in data/raw/. Every cleaning step reads from raw/, transforms in R, and writes to processed/.

This way, the path from messy original to clean dataset is always reproducible: delete processed/, re-run the script, get it back.

R scripts

Beyond Quarto

So far you have written everything in Quarto (.qmd) files: prose, code, and output woven together.

An R script (.R) is different: it is pure R code, no YAML, no markdown, no chunks.

Comments start with #; everything else is code that runs top to bottom.

What a script looks like

# 01-data-preparation.R
# Clean the raw survey data

library(tidyverse)

raw <- read_csv("data/raw/survey.csv")

clean <- raw |>
  filter(!is.na(value)) |>
  mutate(date = ymd(date))

write_csv(clean, "data/processed/analysis.csv")

Script or Quarto?

R script

  • A job to run start to finish
  • Data cleaning, downloads
  • No narrative needed
  • Produces files, not a report

Quarto

  • A document to read
  • Analysis with explanation
  • Prose, figures, tables
  • Renders to HTML or PDF

A common pattern: scripts prepare the data, Quarto reports on it.

Running a script

  • In RStudio: the Source button, or Ctrl/Cmd + Shift + S
  • Line by line: Ctrl/Cmd + Enter, just like in a chunk
  • From another file: source("R/01-data-preparation.R")

source() runs the whole script, as if you had typed every line.

Integrating scripts with Quarto

Keep the heavy lifting in a script, then call it from your report:

```{r}
#| label: prepare
#| include: false

source("R/01-data-preparation.R")
```

The script writes analysis.csv; the report reads it:

```{r}
analysis <- read_csv("data/processed/analysis.csv")
```

Why split the work?

  • The report stays focused on results, not cleaning code
  • Slow preparation runs once, not on every render
  • The same clean data can feed several reports
  • Each file has one clear job

This is exactly the structure of the capstone project: a preparation script in R/, a report in docs/.
